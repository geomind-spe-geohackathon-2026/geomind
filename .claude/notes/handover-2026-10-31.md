# geomind handover: everything decided, built and still to do (2026-10-31)

This file is for a new team member and their Claude. It holds everything Sahand and Claude decided about geomind, why each decision was made, what is built, which interfaces are frozen, and the remaining work in order. Read it fully before changing the repository. Inside the repository, the same content lives in `.claude/docs/plan.md`, which is the source of truth once it lands. If the two differ, the repository wins.

## 1. The goal

The project is the SPE Europe Energy GeoHackathon Express, built on the GEMINI geothermal digital twin.

- **Challenge 1 (50 %):** an agentic AI workflow. It analyses the problem, drives GEMINI, chooses and runs models, fills in missing models, compares alternatives and explains the configuration.
- **Challenge 2 (50 %):** an integrated deep-geothermal heating and cooling design. Report the capacities, the design and the agent log: prompts, answers and token usage.
- **Bonus:** multi-agent work, optimisation, uncertainty, techno-economics and automatic verification.
- **Deliverables:** a report of at most 5 pages or 10 slides, a video of at most 5 minutes, and everything committed and pushed to GitHub.

### Official inputs (released 2026-10-29)

The files are `GEMINI_Heating_Demand_Daily_2027.csv`, `GEMINI_Cooling_Demand_Daily_2027.csv` and `GEMINI_Hackathon_Challenge_Requirements.pdf`. Sahand has them in `crust-team/inputs/`.

| Item | Value |
|---|---|
| Heating demand | 365 daily values; peak 30.0 MWth (28 Jan), minimum 2.67, 111.7 GWh per year |
| Cooling demand | peak 10.0 MW (19 Jul), 23.7 GWh per year, above 0 on 219 days; heating + cooling ≤ 30 on any day |
| Reservoir | mid depth 2500 m TVD, 100 m thick, gradient 30 °C/km, surface 12 °C (so 87 °C at 2500 m), 250 barg, 200 mD; the depth may be chosen |
| Brine | 1030 kg/m³ and 0.40 mPa·s; gas-liquid ratio 0.8 Nm³/m³; gas is 80 % CH₄ and 20 % CO₂ |
| Hard limits | 1 to 3 doublets; 50 to 300 m³/h per doublet while active; brine cooling ≤ 40 K; pump efficiency 70 %; production volume = injection volume; 330 operating days |
| Supply temperatures | 100 °C for heating, 20 °C for cooling (return temperatures are not given) |

What this implies: 87 °C is below the 100 °C supply, so the design needs a heat pump, a gas boiler burning the co-produced gas, or deeper wells (about 3000 m gives about 102 °C). One doublet gives at most about 14 MW at 40 K, so the peak needs 2 to 3 doublets or top-up heat.

## 2. Repositories and how they depend on each other

Local workspace: `crust-team/` with `gemini/`, `geomind/`, `backend/`, `frontend/`, `infrastructure/`, `docs/` and `inputs/`.

```text
frontend (React + Vite) -> backend (FastAPI, Celery) -> geomind (agents) -> gemini (physics)
```

- **gemini** (`import gemini as gm`) is the physics library and engine: modules, plants, units, simulation, results, economics and checks. It is the only place where physics and numbers live. Sahand develops it on the branch `refactor`.
- **geomind** (`import geomind as gd`, repo `git@github.com:crust-team/geomind.git`) is the agent harness and this repository: agents, an engine over an event log, tools, permissions, a sandbox and the `Run` facade the backend uses. **geomind computes no physics.** Every number comes from a gemini tool.
- **backend** stores chats, runs, events and plants, queues runs on Celery and streams events by SSE. It implements geomind's `RunStore` and `Workspace` and never chooses agents or loops.
- **docs/** holds the shared documents. The most important one is `contracts.md`, which every repository follows.
- On PyPI, the name `geomind` belongs to an unrelated, abandoned package. Install locally only, and never publish.
- GeoMind is the product and infrastructure name. The first package name no longer exists anywhere.

## 3. How geomind is built, and why

### Layers

Prompt ⊂ context ⊂ harness ⊂ loop.

- The **prompt** is one agent's instructions.
- The **context** is everything sent in one LLM call: system prompt, tool schemas, history and problem state.
- The **harness** is the engine, tools, permissions, hooks, sandbox and log.
- A **loop** decides which run comes next and when the goal is met.

### The gemini parallels

geomind copies gemini's structure on purpose, so one mental model covers both.

| gemini | geomind | Meaning |
|---|---|---|
| `Module`, one tick | `Agent`, one decision | declarations in `__init__`, behaviour in `forward` |
| `Engine` | `Engine` | drives the unit over steps, finite |
| `optim` | `loops` | algorithms over the engine |
| `backends` | `providers` | implementations behind one protocol |
| `ops` | `tools` | the primitive actions |
| `Callback` | `Callback` | observers |

### Key decisions (each one is settled; change it only with Sahand)

1. **The event log is the only source of truth.** There are no checkpoints. Every LLM completion and every tool result is saved as an event *before* the engine acts on it. Resume, crash recovery and replay are one mechanism, `recover(events)`, and `apply(state, event)` is the only code that changes run state. Any process can continue a run. *Why:* the Managed Agents, LangGraph and Pydantic AI designs (see `research/open-source-harnesses.md`); one mechanism instead of three.
2. **The core is async and the facade is sync.** `run.start()` and `run.resume()` are sync; `astart()` and `aresume()` exist for async callers. *Why:* parallel tool calls and delegates; changing this later would touch every layer.
3. **LLM calls and tool calls are the only side effects.** Everything else is deterministic code over the log, so a durable executor could wrap them later.
4. **Context is explicit.** Tools whose first parameter is `context` get `context.session` (workspace, store, run) and `context.usage`. There is no hidden active-run variable, and `runtime.py` holds settings only.
5. **Hooks and permissions are separate.**
   - Hooks (`before_llm_call`, `before_tool_call`, `before_finish`) receive `context` and return `None`, `Allow(input)`, `Deny(reason)` or `Request(...)`.
   - Every tool declares an effect: `read`, `compute`, `write`, `execute` or `external`.
   - The modes are `auto`, `ask` (the default), `readonly` and `plan`.
   - The fixed order is: hooks, then deny rules, then readonly/plan, then ask rules, then allow rules, then the mode.
   - Every decision is a `permission` event.
6. **There is a sandbox for model-written code.** The `Sandbox` and `SandboxProvider` protocols have two implementations: `LocalSandbox`, for development only, and `DockerSandbox`. A sandbox is provisioned lazily, and credentials never go inside it. A module written by the model only ever runs inside the sandbox, never in the harness process.
7. **There are few generic tools, not one per gemini module.** About 45 modules as 45 tools is the "bloated tool set" failure mode. Tools are generic: list or describe a module, evaluate, build or read a plant, simulate, read a result, and so on. *Errors are results:* a gemini error comes back to the model as an error result, so the model can fix its call, and anything else is a bug.
8. **The problem state** (`ProblemState`) holds `goal`, `requirements` (testable: metric, target, tolerance, status), `assumptions` (value, source, confirmed), `design`, `results` (summary plus a reference to the stored data), `verification` and `questions`, plus a `version`.
   - The model writes it only through `update_state(changes)`, which takes JSON Patch operations exactly as the contract's `state.changed` event. Lists with an `id` are addressed by id.
   - It is rendered last in the context, so the cached prefix stays stable.
   - It is saved per chat, and compaction never touches it.
9. **Long conversations.** Past 60 % of the model window, older turns become one summary made by the `Summarizer` agent. The last 6 turns stay verbatim, and an internal `compaction` event records the change. **Skills** are `.md` instructions loaded on demand with `read_skill(name)`; the system prompt lists only their names.
10. **Agents.** An agent's constructor has the sections `# Agents`, `# Prompt`, `# Tools`, `# Output`, `# Model`, in that order. Assigning an attribute registers it. A child agent is used through a `Delegate` tool or by a loop. There is no `Team` class, because the order of agents is a policy, and policies are loops. An agent declares *which model*; the run supplies *which provider*.
11. **Routing.** `geomind/run.py` holds two tables, `LOOPS` and `AGENTS`. Later, the `Coordinator` returns a typed `Route(kind="answer" | "loop", loop, agent, brief)` with one cheap LLM call, logged as a normal step. **The backend never chooses the loop or the agent.** `gd.Run(agent=...)` exists only for manual testing.
12. **Events.**
    - The public events go to the frontend by SSE: `run.started`, `step.started {index, model}`, `text.delta`, `tool.started`, `tool.finished`, `step.finished {index, usage, text}`, `state.changed {version, changes}`, `request {request, call_id?, kind, message, options [{value, label}]}`, `usage` and `run.finished`.
    - The internal events are `llm.completed`, `tool.result`, `permission`, `retry`, `sandbox.provisioned`, `sandbox.closed`, `error` and `compaction`.
    - Stores save the full `event.to_dict()`, and `gd.event_from_dict` rebuilds an event.
    - `text.delta` is never stored, so stored sequence numbers can have gaps.
    - Nested runs share the root run's log.
13. **geomind uses only gemini's public API** (`import gemini as gm`), never internal paths. gemini's current public names are listed in `gemini/.claude/docs/api.md`. That file is the reference for every gemini tool.

### gemini's API conventions that geomind's tools must follow

These were agreed in the gemini threads on 2026-10-30. Check the current names in `gemini/.claude/docs/api.md`.

- **Versioning.** The version is `gm.__version__` and follows semver below 1.0, so a breaking change raises the minor version. Adding or removing modules in the catalogue is not an API change.
- **Three return shapes only:**
  - **Value** `{value, unit}`, where `value` is a number, an array or `null` (with a `reason` when it is `null`). A series adds `time`, and statistics are `{min, max, mean}`, each a Value.
  - **Problem** `{path, code, message, suggestions}`, used for every error and validation result.
  - **Check** `{name, passed, value, limit}`.
- **Errors.** `on_error="raise" | "record"`, with `raise` as the default. There are seven classes: `GeminiError`, `ValidationError`, `DefinitionError`, `PhysicsError`, `RunError`, `Cancelled` and `NotImplementedYet`. The detail is in `code`.
- **Running.** `gm.simulate`, `gm.replay` and `gm.live(plant, ...)` are thin functions over `gm.Engine`, which stays public. `gm.evaluate` runs one module.
- **Plants.** `gm.plants.from_dict`, `plant.to_dict`, `validate` and `schema`. Well-known plants are registered `gm.Plant` subclasses (for example `Doublet`, which takes design parameters such as depth and gradient). There are no templates. Wiring follows the rules below.
- **Wiring.** Every port is named `<role>_in` or `<role>_out`, and no port may be left unconnected. Everything in the energy flow is a module. Grids (`ElectricityGrid`, `GasGrid`, `HeatingGrid`, `CoolingGrid`, `WasteGrid`) and `Atmosphere` are the plant's boundaries. Plant totals come from the boundary ports.
- **Other names.** `gm.profiles` holds the official demand profiles. `gm.schedule(plant, demand, rules)` builds a run input. `gm.checks.Limits().add(path, min, max)` with `gm.checks.limits(...)` checks limits. `gm.kpi.compute` and `gm.kpi.names` give the KPIs. Economics functions take `(plant, results, assumptions)`. `gm.testing.check_module(cls)` returns a report.

## 5. Frozen interfaces

Sahand's rule: **the interfaces are fixed now, so the backend never breaks later.** The freeze prompt (`phases/geomind/freeze-and-handover.md`) pins each item below with a snapshot test. After that, a change to any of them needs, in the same commit:

- a version raise (`gd.__version__`, semver below 1.0, so a breaking change raises the minor version);
- an updated snapshot;
- a `CHANGELOG.md` entry;
- a note to Sahand, because `docs/contracts.md` must change too.

**Facing the backend** (contracts.md sections 2 and 3):

- `gd.Run(...)` and its methods `start`, `astart`, `Run.load`, `resume`, `aresume`, `cancel`;
- `RunResult` (`run_id`, `status`, `answer`, `request`, `usage`, `stop_reason`, `message`);
- the `RunStore` protocol (7 methods), the `Workspace` protocol (`plant`, `documents`), `LLM.complete`, `Callback.on_event`, `gd.Permissions`, and `gd.hooks.TokenBudget`, `RequireApproval` and `Cancellation`;
- every event type and its JSON;
- the answer shapes, the problem-state document and `gd.runlog`.

**Facing the agent developer:**

- the `Agent` declarations, `Prompt`, `Model`, `Output`, `Route`, `Tool` and `@tool`;
- **the complete tool catalogue up to S4**: names, input schemas and effects. A tool that is not built yet keeps its final signature and returns a `not_implemented` error result;
- the names in `LOOPS` (`tool`, `design`, `makerchecker`, `compare`);
- the eval task format;
- the `geomind chat` commands.

The JSON schemas of the exchanged documents live in `geomind/schemas/`, with sample files for each.

## 6. Remaining work, in order

### S2b: gemini tools (the first job for the new member)

1. Implement the gemini tools against gemini's current public API (`gemini/.claude/docs/api.md`). Use only `import gemini as gm`. Return gemini's three shapes unchanged. Turn every gemini error into an error result in the Problem shape.
2. `FileWorkspace.plant` loads plants through `gm.plants.from_dict`.
3. Give the `Analyst` its gemini tools, update the `gemini-units` skill to the units gemini accepts, and write the first eval tasks on the example doublet:
   - the operating point;
   - heat delivered at 150 m³/h;
   - a missing parameter that needs `ask_user`;
   - a module lookup;
   - the ESP at another frequency.
4. Make one live run (`geomind chat --agent analyst --live`) and record it. Report the token cost.

### S3: design agents and verified loops (Challenge 2)

- **Verifiers** call gemini checks only and never an LLM:
  - energy and mass balances;
  - demand coverage per day;
  - bounds and limits, including the hard limits in section 1;
  - unit consistency.
- **Fill the skeleton agents:** `Designer` proposes configurations and sizes; `Verifier` runs the checks and reviews; `Economist` gives capex, opex, LCOH, LCOC, NPV and CO₂ through gemini; `Explainer` writes the user-facing explanation; `Coordinator` routes.
- **Loops:**
  - `DesignLoop`: propose, simulate, verify, write the failures to the problem state, and repeat until everything passes, the budget runs out, the round limit is reached, the same check fails repeatedly, or a question goes to the user.
  - `MakerCheckerLoop`: the designer proposes and the verifier checks.
- **Agent-written modules (Challenge 1):** the `test_module(path)` tool runs `gm.testing.check_module` in the sandbox, and the `writing-a-gemini-module` skill comes from gemini's module guide.
- **No design reaches the user without passing every verifier.** Every stop reason is explicit and logged.
- *Done when* `geomind run --loop design <brief>` returns a verified design with capacities, a description of the schematic, the numbers and an explanation for the official brief.

### S4: compare, uncertainty, evals and export

- `CompareLoop` runs `DesignLoop` on alternatives in parallel and ranks them on cost, CO₂ and coverage. Example alternatives: cooling by heat pump, absorption chiller or compression chiller; with or without storage; 2 or 3 doublets.
- **Uncertainty (bonus):** run the chosen design over P10, P50 and P90 reservoir and demand cases.
- `evals/tasks/challenge2/`: the official brief plus variants (more cooling, a colder reservoir, a tighter budget). `evals/reports/summary.md` compares `ToolLoop`, `DesignLoop`, `MakerCheckerLoop` and `CompareLoop` on criteria met, steps, tokens, cost and time.
- `geomind show <run> --format md` exports the agent log in the form the competition asks for: prompts, answers and token usage.

## 7. How to work in this repository

- **Read first:** `AGENTS.md` and every file in `.claude/docs/`.
- **Branch:** work and push on `main` directly. Do not create other branches.
- **Code quality:**
  - nesting at most 3 levels, functions about 40 lines at most, flake8 complexity 10;
  - guard clauses, full-word names and explicit `gd.errors` classes;
  - no dead or speculative code, and no golfed code;
  - **no comments inside code**: only docstrings and `NOTE:`;
  - simple public API, complexity hidden inside;
  - write a failing test before each bug fix.
- **Tests:**
  - while working, run only the tests of the changed files and of their importers, in parallel (`make test`);
  - before each commit, run the fast suite;
  - a fast test takes 1 s at most, and no test ever calls the network.
- **Docs:** a commit that changes behaviour updates `AGENTS.md` or `.claude/docs/` in the same commit.
- **Temporary files** go to `.tmp/`.
- **Subagents** use lighter models.
- **Stop and say so** when something is missing or risky. Never guess a gemini name.
- **Never change** `gemini/`, `backend/`, `frontend/`, `infrastructure/` or `docs/contracts.md` from this repository. Report what they need to Sahand.
- **Credentials** never go into prompts, events, logs, the sandbox or memory.
- **Testing an agent by hand:** `geomind chat --agent <name> [--live | --recording FILE] [--project PATH] [--model ID]`, with the commands `/state`, `/log`, `/reset` and `/quit`.
- **Testing an agent by tasks:** write `evals/tasks/<agent>/<task>.yaml`, run `python -m evals.run --agent <name> --live` once to record it, then run offline.
- **Adding or filling an agent:** follow `.claude/docs/agents.md`. The `Analyst` is the worked example.
